# Physics Events for Entities 性能検証記録

Unity 6000.3.22f1、Entities / Unity Physics 1.5.0、Burst 1.8.30、Collections 2.7.1、11th Gen Intel(R) Core(TM) i7-1185G7 @ 3.00GHzで検証しました。IL2CPPは対象外です。[測定結果JSONとソースハッシュ](PerformanceResults.json)を保存しています。

## 速度を優先した変更

6種類のEnableable DynamicBuffer、PhysicsEventReceiverAuthoring、容量設定、SystemAPI.Queryの公開APIは維持しています。利用コードとInspector設定の変更は不要です。

比較前構成では各Entityの範囲を登録してから、書き込み側で前回・今回の履歴をマージしていました。現行構成は履歴の比較時にEnter／Stay／Exitを一度だけ判定し、購読中の種類だけを連続通知リストへ格納します。対象表の値は購読マスクと通知の開始・件数に変更しました。書き込み側はこの範囲を参照して、各チャンクが所有するBufferへコピーします。

作業領域のClearも1つのJobに統合しました。Bufferの有効状態はGatherで確定し、同じ依存鎖で通知を作ります。書き込み側での有効マスク再取得と履歴マージを省きます。Bufferアクセスは通常のECS依存関係で保護し、任意Entityへ並列Lookup書き込みを行う方法や、安全性チェックを無効化する属性は使用していません。

さらに、収集直後の接触列を保存します。今回と要素数・順序・self／other双方のIndexとVersionが完全一致すれば、前回のソート・重複除去済み履歴をコピーし、ソートと重複除去を省略します。通知と購読マスクは毎固定更新で作り直すので、Enterが繰り返されたり古い通知が残ったりすることはありません。接触や順序が変われば通常処理へ戻ります。ハッシュ値での近似判定は使いません。

## 同じ1万体の実Collision条件

比較前構成も同じ条件で測定しました。10,000個の動的Boxと床、ブロック上のプレイヤー1体を使用します。各測定・GC測定固定更新で床―ブロック10,000組とプレイヤー―ブロック1組、合計10,001組の実Collisionを区間外で監査しました。全対象受信は10,001体、1 Systemあたり10,002件の通知です。

64固定更新の物理ウォームアップ、32固定更新のパッケージウォームアップ後に32固定更新×3試行を測り、各試行の中央値3値の中央値を示します。GCは別の32固定更新で測定します。Collectは準備・購読表構築・収集・履歴比較・通知作成・書き込み・Job完了待ちを含みます。Packageは容量確保Systemと利用Systemの読み取りも含み、Unity Physics本体は除きます。通常構成の値です。

| 条件 | 比較前 Collect ms | 現行 Collect ms | 比較前 Package ms | 現行 Package ms |
| --- | ---: | ---: | ---: | ---: |
| 購読なし | 0.0050 | 0.0046 | 0.0169 | 0.0161 |
| プレイヤー1体 / 1 System | 0.2551 | 0.2525 | 0.3078 | 0.3054 |
| プレイヤー1体 / 16 System | 0.2321 | 0.2470 | 0.3377 | 0.3462 |
| プレイヤー1体 / 64 System | 0.2275 | 0.2284 | 0.5004 | 0.4897 |
| 全対象 / 1 System | 0.8947 | 0.7661 | 1.5174 | 1.1729 |
| 全対象 / 16 System | 0.9123 | 0.8384 | 7.2005 | 6.5865 |

全対象・1 SystemのCollectは0.8947→0.7661 ms（14.4%短縮）、全対象・16 Systemは8.1%短縮でした。少数受信の差は小さく、全条件での一律な高速化とは扱いません。利用System数が多い条件では、利用側の読み取り時間が全体の大きな割合を占めます。物理本体の時間・各サンプル・試行日時も生データに保存しています。batchmode / nographicsのEditor測定であり、他プロセスやスケジューリングのばらつきを含みます。

## メモリとGC

| 領域（全対象受信） | 比較前 B | 現行 B |
| --- | ---: | ---: |
| 前回・今回の接触履歴 | 524,288 | 524,288 |
| 収集直後の列のスナップショット | 0 | 262,144 |
| 連続通知リスト | 0 | 196,608 |
| 対象キーと範囲・購読マスク | 240,024 | 200,020 |
| 公開Bufferの予約データ | 1,920,192 | 1,920,192 |
| 保持データ量の下限 | 2,684,504 | 3,103,252 |

全対象で418,748 B（約0.42 MB）の保持データ増加を採用しました。プレイヤー1体は728→1,172 B、未購読は両方0 Bです。この下限はコンテナヘッダー、HashMapのbucket・next・アラインメント・TLS、アロケータ管理領域、容量設定Component、ECSチャンク、物理本体を含まず、Nativeメモリ総量ではありません。UnityAllocatorActivationDeltaBytesも保存していますが、Editor全体の変動を含みます。

通常構成では計測用NativeReference・チャンク別計測配列・集計Jobをコンパイルしません。全通常条件でcurrent-threadのGC.Allocは0回・0 B、測定前後の保持容量差は0 Bでした。ProfilerRecorderは別途1024 Bを割り当てる対照で検出を確認しています。計測構成では収集・履歴比較・書き込みのManaged fallback 0、定常時の接触・通知・対象表・スナップショット・公開Buffer等の再確保0回を確認しました。未購読時は収集スケジュール0回・接触保存領域0 Bです。

最後の有効な購読がなくなると、履歴・スナップショット・通知・対象表を解放します。公開Bufferの予約容量は維持します。再購読での再確保と、予約容量を超える接触増加によるNative再確保は発生し得ます。

## Authoringと自動テスト

通常構成のPlayMode 38件、PHYSICS_EVENTS_PROFILING指定構成のPlayMode 38件、EditMode 4件が成功しました。Enter／Stay／Exit、Compound重複、Entity破棄・再利用、Enableable、複数FixedStep、通常QueryとJob、購読終了・再購読、Prefab、実SubSceneのロード・再ロードを検証しています。

現行構成では、1 Entityが1,024接触を重複なく受信するケース、不要なStay／Exit通知を内部にも作らないケース、購読マスク変更、完全一致判定の順序・Index・Version、安定接触での再利用と離脱でのExitを追加検証しました。

実Bakerで標準Rigidbody・BoxCollider・受信AuthoringをBakeし、10,001体へInstantiateする4条件×3試行も測定しました。Baker由来のComponent構成等が異なるため、手動生成条件の時間とは分けます。各固定更新で10,001組の実Collisionを監査しました。

| Authoring条件 | Package ms | 公開Buffer予約データB | 履歴・スナップショット・通知・対象表B |
| --- | ---: | ---: | ---: |
| AllThree | 2.3976 | 1,920,192 | 1,183,060 |
| EnterOnly | 1.5926 | 640,064 | 1,183,060 |
| None | 0.0316 | 0 | 0 |
| PlayerOnly | 0.3301 | 192 | 980 |

Noneは未購読、PlayerOnlyはプレイヤーだけ3種類、AllThreeは全対象に3種類、EnterOnlyは全対象にCollisionEnterだけを追加します。GCはいずれも0 Bです。生成、初回予約、初回収集時間も生データに記録しています。

## 制限と再実行

- 再利用が有効なのは接触列が完全一致するときです。物理イベントの順序が変わる場合や接触が頻繁に増減する場合は通常処理へ戻り、比較・スナップショットコピーの追加費用が発生します。そのような負荷全般での高速化は保証しません。
- 同じEntity同士の接触を扱い、Collider単位の情報は公開しません。イベント順序への依存は避けてください。
- HavokとIL2CPPは検証対象外です。

通常構成でPlayModeのPhysicsEvents.Entities、EditModeのPhysicsEvents.Entities.Tests.Editorを実行します。詳細カウンターを記録する場合はPHYSICS_EVENTS_PROFILINGを指定し、通常測定と区別してください。ベンチマーク出力先はPHYSICS_EVENTS_BENCHMARK_DIRECTORYで変更できます。
